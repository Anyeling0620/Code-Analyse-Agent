## 2. 指标（45 题，文件级）

`F@k` = 期望文件出现在前 k 名的题目比例；`MRR` = 期望文件名次倒数的均值。

| arm | F@1 | F@5 | F@10 | F@20 | MRR | p50 (ms) | p95 (ms) |
| --- | --- | --- | --- | --- | --- | --- | --- |
| `dense_zh` | 0.2889 | 0.7333 | 0.8222 | 0.9111 | 0.4602 | 288 | 371 |
| **`dense_en`** | **0.6444** | **0.8889** | 0.9111 | 0.9111 | **0.7395** | 279 | 317 |
| `sparse_zh` | 0.1333 | 0.2444 | 0.3556 | 0.4889 | 0.2048 | 28 | 36 |
| `hybrid_zh` | 0.4444 | 0.8444 | **0.9333** | **0.9333** | 0.6181 | 770 | 886 |
| `hybrid_en` | 0.5111 | 0.8222 | **0.9333** | **0.9333** | 0.6473 | 791 | 900 |
| `hybrid_zh_norerank` | 0.2444 | 0.4000 | 0.6000 | 0.8667 | 0.3396 | 305 | 360 |
| `hybrid_en_norerank` | 0.3333 | 0.7333 | 0.8222 | 0.9111 | 0.4747 | 279 | 351 |

arm 命名含义：`zh` = 原始中文查询，`en` = 单句英文改写后查询，`dense` = 纯向量，`sparse` = 纯 BM25，
`hybrid` = 两路 RRF 融合 + 重排，`_norerank` = 关掉重排（纯 RRF 排序）。

## 3. 优化前后对比（同一索引、同一评测集内的有效对照）

### 3.1 重排开关

同索引、同候选池，只切 rerank 开关：

| 对比 | F@1 | F@5 | F@10 | MRR |
| --- | --- | --- | --- | --- |
| `hybrid_zh_norerank` → `hybrid_zh` | 0.2444 → **0.4444**（+20.0 pp） | 0.4000 → **0.8444**（+44.4 pp） | 0.6000 → **0.9333**（+33.3 pp） | 0.3396 → 0.6181 |
| `hybrid_en_norerank` → `hybrid_en` | 0.3333 → **0.5111**（+17.8 pp） | 0.7333 → **0.8222**（+8.9 pp） | 0.8222 → **0.9333**（+11.1 pp） | 0.4747 → 0.6473 |

**结论：重排必须保留。** 代价约 0.5 s/次（p50 从 305 ms 升到 770 ms），换来 F@1 +20 pp。

### 3.2 中文 → 英文单句改写

| 对比 | F@1 | F@5 | MRR |
| --- | --- | --- | --- |
| `dense_zh` → `dense_en` | 0.2889 → **0.6444**（**+35.6 pp**） | 0.7333 → **0.8889**（+15.6 pp） | 0.4602 → **0.7395** |
| `hybrid_zh` → `hybrid_en` | 0.4444 → **0.5111**（+6.7 pp） | 0.8444 → 0.8222（−2.2 pp） | 0.6181 → 0.6473 |

**结论：这是全表证据最强的单项优化**，且改写本身只增加约 0.3 s（`dense_en` p50 279 ms，
甚至略快于 `dense_zh` 的 288 ms，说明改写带来的收益不是靠牺牲延迟换来的）。

注意：收益集中在**纯向量路径**（+35.6 pp）；混合检索路径上只有 +6.7 pp，因为 RRF 融合会稀释它。

### 3.3 候选池（当前状态，非前后对比）

| 对比（同索引） | F@20 |
| --- | --- |
| `hybrid_zh` vs `dense_zh` | 0.9333 vs 0.9111 |
| `hybrid_en` vs `dense_en` | 0.9333 vs 0.9111 |

**融合不再丢目标**：混合检索的候选覆盖不低于单路。候选池配置为 dense 40 / sparse 40 / 融合 40。

## 4. 关键结论

### 4.1 短板在排序，不在召回

```
F@1 ：dense_en 0.6444  >  hybrid_en 0.5111  >  hybrid_zh 0.4444  >  dense_zh 0.2889
F@10：hybrid_en 0.9333  =  hybrid_zh 0.9333  >  dense_en 0.9111  >  dense_zh 0.8222
```

`hybrid` 的 **F@10 与 F@20 完全相等（都是 0.9333）**——正确答案几乎总在前 10 名里，
但排进第 1 名的只有 44%。**再提高召回率没有意义，该改的是排序。**

### 4.2 当前最优组合是「改写 + 纯向量」，不是「hybrid + 重排」

`dense_en` 拿下 F@1 / F@5 / MRR 三项最优（0.6444 / 0.8889 / 0.7395），
而完整的 `hybrid_en` 只有 0.5111。hybrid 只在 F@10 / F@20 上反超。

**即：hybrid + 重排在 top-1 上是净损失**，它把一部分原本排第 1 的正确文件挤到了后面。

### 4.3 RRF 丢弃分数本身是负收益，靠重排才被救回来

RRF-only 低于同一查询的单路 dense：

| 对比 | RRF-only | 单路 dense |
| --- | --- | --- |
| 中文 F@1 | `hybrid_zh_norerank` 0.2444 | `dense_zh` 0.2889 |
| 英文 F@1 | `hybrid_en_norerank` 0.3333 | `dense_en` 0.6444 |

RRF 只用名次、丢弃相似度分数，融合后排序反而变差；是重排把它拉回到可用水平。
**所以这一段（融合 + 重排）是下一步该动的地方，而不是继续增加检索路径。**

### 4.4 中文自然语言密集的文件被系统性过采

统计 `dense_zh` 的 top-5 槽位（45 题 × 5 = 225）里各文件出现次数，与其语料占比对比：

| 文件 | 语料占比 | top-5 占比 | 过采比 | 文件中文占比 |
| --- | --- | --- | --- | --- |
| `service/agent/runner/prompt.go` | 0.6% | 11.1% | **17.7×** | 42.8% |
| `service/projectid/projectid.go` | 0.8% | 8.9% | **11.0×** | 7.9% |
| `web/prompt.md` | 0.4% | 3.1% | **8.7×** | 67.4% |
| `service/agent/db_report/prompt.go` | 0.5% | 4.0% | 7.4× | — |
| `web/src/App.tsx` | 2.4% | 12.4% | 5.1× | 0.89% |

两类互不相同的机制：

1. **中文文本密度**：中文 query 直接与中文散文重合。
2. **hub 大文件**：chunk 数多则出现机会多（`App.tsx` 27 块 = 语料 2.4%，占 top-5 的 12.4%）。

这两类文件几乎从不包含"XX 实现在哪"的答案，却稳定霸占前排。换成别人的仓库时，
对应物是 `README.zh.md`、`docs/`、i18n 资源、prompt 模板、超大单文件，而它们在真实项目里的占比通常更高。
**中文提问场景下，这是与"跨语言鸿沟"并列的第二个系统性偏差来源**，也解释了为什么 F@10 能到 0.93 而 F@1 只有 0.44。

## 5. 口径与限制（引用上面的数字必须一起带上）

1. **符号级 `S@` 指标已废弃，并已从本报告移除。** 原判定逻辑
   （`symbol == want || strings.Contains(doc.Content, want)`）不校验命中文件，
   会产生 `sparse_zh` 的 `S@1 = 1.0` 而 `F@1 = 0.0` 这种自相矛盾的结果。
   **只看 `F@` 系列与 `MRR`。**

2. **ground truth 有效度 44/45（文件级）。** 其中 1 题（`f001`）的目标文件
   `utils/dsml/eino_compat_test.go` 已不在索引里——测试文件不再纳入版本控制后，克隆中就没有该文件；
   另有 2 题（`f006` / `f036`）的目标符号被合并或改名（文件级仍可能命中）。
   因此**文件级 F@1 的理论上限约 0.978**，不是 1.0。

3. **评测集是 45 题的兜底自造集，不是权威基准。** 题目由 LLM 生成，覆盖面有限，样本量小
   （45 题里 1 题 = 2.2 pp）。

4. **被索引的是本仓库本身**，`.go` 占 80.8%，而 Go 是唯一走真 AST 精确切分的语言。
   **绝对数字偏乐观**，只适合同一索引内的相对比较，不能对外引用。

5. **评测集文件绝不能被索引进被评测的语料**，否则查询与语料逐字重合，
   问题清单会霸占 rank-1，使全部指标失真。已通过取样阶段跳过 `eval/`
   （连同 `testdata/`、`fixtures/`、`benchmark(s)/`）修复。

## 6. 复现

```bash
# 全量（7 条 arm，45 题）
go run ./eval/rag

# 冒烟（内置 3 题，验证各臂能出结果）
go run ./eval/rag -smoke

# 核对评测集目标是否还在索引里（缺失会打印 PATH-MISSING / SYMBOL-MISSING）
go run ./eval/rag -check

# 导出 collection 全量 chunk 元数据快照（只读）
go run ./eval/rag -dump

# 只跑指定 arm、或全局关闭重排
go run ./eval/rag -arms dense_zh,hybrid_zh -no-rerank

# 把本轮对照表写回本文件
go run ./eval/rag -report eval/rag/REPORT.md
```

其它可用参数：`-topk`、`-limit`、`-dense-topk`、`-sparse-topk`、`-candidate-k`、
`-rerank-topn`、`-rewrite-arm`、`-gen N`（兜底出题）。

产物：`results.json`（原始结果）、`collection_index.json`（元数据快照）。
两者均在 `.gitignore` 中，不入库。
