## 一、类/方法级符号识别：结构增益成立，检索增益**未获证实**

### 1.1 改动

`service/rag/chunker.go` 的 `splitBraceSymbols` 原来只在**大括号深度归零**处切块，类方法位于类体内部（深度 1），因此整个类被当成一个大块、超长后被行窗二次切，产生多段语义不完整的窗口。

改后：识别 `class` / `export class` / `export default class`，下钻类体，把每个方法（普通方法、`async`、`static`、getter/setter、箭头函数类字段）切成独立块，`symbol = Class.method`、`parent = Class`、`kind = method`，并带正确的 `line_start/line_end`。

既有约束全部保留：同行开闭的花括号不成块、import 清单不成块、块尾不落在行中间、不可靠时回退盲切、Go 路径不受影响。

`lib/core/Axios.js` 的变化最直观：

**这一层是确定的增益**：方法级块从 0 到 137，行区间自洽（逐块回读源文件比对一致），元数据可用于 `file:符号` 级引用。

**结论：不能说带来了检索增益。**

- F@1 两升两降三平，F@10 两升两降三平，MRR 两升三降一平
- 只有 **F@20 是 4 升 1 降**（深度召回方向偏正）
- **n = 20，1 道题 = 5 pp——上面这些幅度就是噪声地板**

### 1.4 而且我的预判被证伪了

改动前的判断是："`Axios.js` 的类体碎片化挡住了方法级检索，修好后那 3 道题（a002/a010/a017）应该能进前排"。

**实际结果：这 3 道题在新索引下仍然一道都没进 top-10，排名变化全在噪声内。**

所以"类体碎片化"**不是**那 3 道题失败的原因。

### 1.5 这一项能站得住的最强表述

> **结构正确性达成**（方法级块 0 → 137、行区间自洽、可按方法引用），
> **深度召回方向偏正**（F@20 四升一降），**精度指标无变化**（在 n=20 的噪声内）。
> 改动的价值在于**元数据可引用性**和为后续父块聚合铺路，**不在当期检索指标**。

不要对外声称"类/方法识别提升了检索准确率"——数据不支持。

## 二、整条 RAG 链路：**通**

### 2.1 四段链路逐段验证

```
repo_fetch 克隆 → 异步索引进 Milvus（独立 collection）→ agent 调 rag_retriever → 跨文件关联
```

### 2.2 跨文件关联：实测成立

axios 语料（3353 块）走生产同一条 `Retrieve` 路径，3 个中文问题：

- **每题的 top-5 都覆盖 4 个不同文件**
- 带行号的命中**逐条回读源文件比对，内容与行号全部一致**

也就是说，检索结果确实横跨多个文件，且引用可回溯到具体行——这是"分析 agent 能利用 RAG 找到跨文件关联"的直接证据。

## 三、期间发现并修复的一个链路级 bug（重要性高于本次功能）

### 现象

重建后集合有 **3353** 条；在**全新进程**里调一次检索，再导出 → **0 条**。而 `Status` 仍然报 `ready`。

### 根因

`Retrieve` 走 `storeFor`，而 `storeFor` 传了 `WithInitCollection(true)`；配置里 `drop_before_index: true`，于是新建 store 时**先执行了 `DropCollection`**。

进程内因为 store 已缓存，看不出来；**服务重启后，第一次使用 RAG 就会把该项目的索引整个清空。**

### 影响

模型看到的是"没有检索到相关内容"，**静默退回 `project_search`，用户侧零提示**。这直接否定了此前"重启后第二轮追问仍能复用索引"的设计假设——而"第一轮分析、第二轮追问吃 RAG"正是我们定下的产品形态。

### 修复与验证

把只读检索视图与索引视图分开：`retrieverStoreFor` 不传 `WithInitCollection`、只建 retriever，并使用独立缓存。

| | 修复前 | 修复后 |
| --- | ---: | ---: |
| 新进程检索一次后的集合条数 | 3353 → **0** | 3353 → **3353** |

端到端测试与全量测试均通过。

## 四、仍然存在、且未解决的缺口

按对**质量**的影响排序：

| # | 缺口 | 证据 |
| --- | --- | --- |
| 1 | **散文过采是当前最大的质量瓶颈** | 3 个跨文件问题里，Q2/Q3 的 top-5 **全是 `docs/`、`README`、`CHANGELOG`**；Q1 命中 3 条 `tests/` 文件但**没有一条落在 `lib/` 实现目录**。这才是 F@1 上不去的真实原因，类成员抽取没有触及它 |
| 2 | **回退路径的块没有行号** | `.md/.json/.yml` 走通用切分器，`line_start = 0`，占 **1426/3353 = 42.5%**；这类命中**无法给出 `file:line` 引用** |
| 3 | **工具返回值不含 symbol / 行号** | `rag_retriever` 的 `formatDocuments` 只输出 `source/chunk/heading`，metadata 里已有的 `symbol/line_start/line_end` **没有传给模型**——模型拿不到"命中在哪个符号的哪几行" |
| 4 | **`Status` 无法发现"集合存在但为空"** | 第三节那个 bug 正是靠这个盲区隐藏了两轮 |

缺口 3 看起来最"便宜且确定"：数据已经在 metadata 里，只是没往工具返回值里放。
